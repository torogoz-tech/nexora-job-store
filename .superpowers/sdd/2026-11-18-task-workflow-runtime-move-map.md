# Task 1 — task workflow runtime move map

Baseline: `nexora-api` develop at `2b9ff4d80f9d4aefde309656ea5b1a97f70e9681`. Paths below are relative to that checkout unless specified. Store modules are in `crates/nexora-platform-store/src`; handlers and MCP dispatch are in `crates/nexora-api/src`. This is an inventory for the approved extraction into `nexora-job-store`, not a change to scheduling, schema, or public contracts.

### MCP dispatch and authorization

| Tool and dispatch target | Adapter and store checks |
| --- | --- |
| `nexora_task_transition_runs` → `WorkItemMcpTools::call` → `ApiState::run` → `PlatformStore::task_transition_runs` | Decode `McpTaskGet`; call `verify_task_project` before listing. The list method separately calls `TaskScopeAuthority::task(TasksRead)` and scopes run rows to the actual task project with `IS NOT DISTINCT FROM`. |
| `nexora_task_transition_retry` → `WorkItemMcpTools::call` → `ApiState::mutate` → `PlatformStore::retry_task_transition` | Decode `McpTaskTransitionRetry`, use configured Git policy and the `task.transition_retry` receipt operation with request ID and canonical input `{task_id, run_id}`. The retry store resolves scope with `TasksTransition`, calls `TaskTransitionRunStore::authorize`, then selects the run by ID, task ID and current actor ID. |
| `nexora_task_take` → `TaskLifecycleMcpTools::call` → `ApiState::mutate` → `PlatformStore::take_task_with_repositories` | Decode `McpTaskTake`, use the `task.take` receipt operation with canonical input `{project_id, task_id, take}`, and pass the optional project and configured Git policy to `TaskCodeStart::execute`. That store method calls `pool_task` and compares the optional project. Without repositories it delegates to `TaskPoolStore::take`, which locks the active human actor, checks `TasksTransition`, project match and assignee eligibility/role. | `nexora_task_approval_get` → `WorkItemMcpTools::call` → `ApiState::run` → `PlatformStore::get_pool_task_approval` | Decode `McpTaskApprovalGet`; call `verify_task_project`. HTTP pool/project take and MCP take reach the same `TaskCodeStart` checks. `ApiState::mutate` uses `PlatformStore::request` for live credential refresh and receipt context before executing its closure, and signals the existing job wake-up after a successful result.

### Approval paths

- Pool and project POST `/tasks/{task_id}/approvals` → `TaskPoolHandlers::approval_grant` / `WorkItemHandlers::approval_grant` → `grant_pool_task_approval(&mut self, ctx: &AuthContext, id: &str, input: &TaskApprovalGrant)` / `grant_task_approval(&mut self, ctx: &AuthContext, project: &str, id: &str, input: &TaskApprovalGrant)`, both `Result<TaskApproval, PlatformError>` → `TaskApprovalStore::grant` → `grant_in`.
- Project POST `/approval-requests/{approval_request_id}/decisions` → `ApprovalRequestHandlers::decide` → `PlatformStore::decide_approval_request(&mut self, ctx: &AuthContext, project: &str, id: &str, input: &ApprovalRequestDecide) -> Result<ApprovalRequest, PlatformError>` → `ApprovalRequestDecisionStore::decide` → `TaskApprovalStore::grant_in` for approved task targets, in the decision transaction. Denial and document targets do not ready a task transition.
- `grant_in` checks human session, current task and graph, independence, parameters and expiry. It inserts the grant and enriches exact matching `waiting_approval` runs with the approval ID, clearing error/message and setting `ready`. It does not itself execute the transition. Lookup and revocation stay on pool/project HTTP approval routes via `TaskApprovalQueryStore` and `TaskApprovalRevocationStore`. Their signatures are `get_pool_task_approval(&mut self, ctx: &AuthContext, task: &str, id: &str)` and `revoke_pool_task_approval(&mut self, ctx: &AuthContext, task: &str, id: &str, input: &TaskApprovalRevoke)`; `get_task_approval` and `revoke_task_approval` add `project: &str` before `task`. All return `Result<TaskApproval, PlatformError>`. MCP `nexora_task_approval_get` reads and does not grant. `verify_approval` validates via `consume` in a rolled-back transaction before provider writes. `advance` consumes in the same transaction as the state mutation.
- Engine `request_approval` creates the project request through `ApprovalRequestDefinitionStore::create` and nested `PlatformStore::request` with outer request context suspended. `ApprovalOperationPolicy` calls the same transition evaluation to validate a task target. Projectless requests use the in-app notification path in the engine. Direct grant also updates matching pending approval requests and history.

## Runtime behavior that must survive the move

1. Continuation selects by the SQL below. It loads the original credential by ID/method via `AuthenticationStore::load`, loads current actor/grants and compares actor ID to the persisted row. Sessions must be ready, human, active, unrevoked, and within idle and absolute expiration. API keys must have an active actor, be unrevoked, be within optional expiry and carry valid scope. Resume does not touch session activity. No row returns `false`. A credential-load error or actor mismatch uses the first terminal patch below. Live Unauthorized/Forbidden/NotFound from retry uses the second. A storage error from retry propagates, while other retry errors return `true` after engine handling where applicable. The selection has no claim lock and does not recover `running` rows.
2. `TaskTransitionEngine::execute` reauthorizes and serializes by session advisory lock `task-transition:{id}`. It also locks the receipt identity when present, releases locks and clears scratch facts/checkpoint on normal result paths. Provider HTTP and Git operate outside the state transaction. Durable run identity is task + expected revision + transition + actor + normalized approval fingerprint. Replays consult receipts, stored outcomes, provider intents, and checkpoints before repeating side effects. The exact writes and recovery boundaries are below.
3. Load the pinned workflow version, validate graph and current task, then authorize through each step. Supported step paths include approval, push/branch and PR verification, create/merge PR, CI pipeline/deployment verification, contributor rating, code review, state advance, handoff, release publication and notification. Where advance consumes evidence, recheck previously observed provider authorities and live task guards under database locks. Persist `advanced`, `result` and `next_step` with the state change. Handoff preserves task identity and records completion/delivery evidence. The post-advance path can rebuild provider evidence before handoff, so it cannot be omitted as an apparent replay optimization.
4. `dispatch_final` can execute the automatic edge after an eligible governed stage reaches Fin. It handles revision drift, excludes decomposition and same-stage corrective work, clears inherited approval and resolution fields for the new edge, and suspends outer request context. A failing automatic action leaves the completed stage result and its durable run. Terminal self-edge runs do not increment the task revision again.
5. Notifications write durable queue rows with event identities derived from run and step and can requeue failed delivery. Preserve migration 0088's failure trigger and the distinction between a failed notification and a failed task advance. Mail delivery itself belongs to notification processing.

### Continuation predicates

```sql
SELECT id,task_id,actor_id,credential_id,auth_method
FROM task_transition_runs
WHERE (record->>'status'='ready'
       OR (record->>'status'='waiting_external'
           AND updated_at<clock_timestamp()-interval '30 seconds'))
ORDER BY updated_at,id LIMIT 1;

UPDATE task_transition_runs
SET record=record||$2::jsonb,updated_at=clock_timestamp()
WHERE id=$1 AND record->>'status' IN ('ready','waiting_external');
```

The age filter applies only to `waiting_external` selection. Both terminal updates use the same status-and-ID predicate, with no age recheck. They set `status=failed` and `error_code=transition_authority_changed`. The credential fallback records “Original execution credential expired or was revoked. Restore authority and retry explicitly.” Retry authorization failure records “Original execution authority changed. Reload the task and retry explicitly.” These are standalone updates with no history or receipt write and no check of the affected-row count.

### Provider intent writes and reconciliation

`TaskTransitionProvider` writes `request_started` via `TaskTransitionRunStore::save` before attempting the provider mutation. Each save is a standalone `UPDATE task_transition_runs SET record=$2,updated_at=clock_timestamp() WHERE id=$1`. A `confirmed` write stores provider evidence separately from the engine's later step-completion save. A stored intent can represent a crash before the request or a lost response, so the provider is consulted on replay:

| Operation | Identity and retry behavior |
| --- | --- |
| Create pull request | Key `{step_index}:{repository_id}`, start intent includes repository ID and expected head. Search all provider states and pages by source/target and the `<!-- nexora-transition:{run_id}:{key} -->` marker. Multiple matches conflict. A match must decode to the exact head/source/target and still be open, with authority unchanged. With no match and an existing intent, report unknown outcome without posting again. A fresh post rechecks task revision, repository binding and source SHA. Only explicit Forbidden, NotFound, Validation or Conflict errors from the post remove the intent and persist the removal. Other errors retain it. Confirmation stores repository ID, PR number and head SHA. |
| Create branch | Key `branch:{step_index}:{repository_id}:{branch_name}`, start intent includes repository, branch, base ref and SHA. An existing destination must equal the pinned SHA. If the base has changed, recovery requires both a prior intent and an existing destination at the pinned SHA. A missing branch with any prior intent is an unknown outcome, and a different SHA is a conflict. On a create error, reread the branch and accept only the exact pinned SHA, otherwise return the error and retain the intent. Verify destination SHA and current source/authority before persisting `confirmed` with branch/base evidence. |
| Merge pull request | Key `merge:{step_index}:{repository_id}:{target}`, start intent includes repository, head, target, PR number and provider readiness. `TaskProviderMerge::find` identifies one matching open or merged PR at the pinned revision and target. `confirmed` requires a provider-confirmed merge and merge SHA. If that proof is absent and an intent exists, return unknown outcome. For a fresh write, verify approval and provider readiness, recheck task/repository/source head, then verify approval again. After the attempt reread the matching PR even if the write errored. If the read confirms merge, use that result. If the read succeeds without confirmation, clear and save the intent only for explicit Forbidden, NotFound, Validation or Conflict from the write. A successful write without confirmation yields `waiting_external` through the failure mapper. A failed reconciliation read or ambiguous write retains the intent. Recheck repository authority before persisting `confirmed` with the merge result. |

When revalidating earlier creation steps at advance, `create_requests` uses `merged_branch` to match a recorded merge outcome by repository, head and target. It re-observes that merged PR with `observe_to` and does not require it to be open again.

### Transaction groups

| Path | Writes that commit together and writes that follow separately |
| --- | --- |
| State advance | `TaskTransitionStore::advance` locks task relations and live authority, consumes approval, updates task state/resolution/revision when applicable, appends task history and audit, and writes the optional `advanced/result/next_step` run checkpoint in one transaction. Migration 0099 records terminal-stage completion via the task update trigger. The helper can write a receipt if given a request context, but the engine suspends that context for `AdvanceState`. The enclosing `execute` reads any previous receipt before execution and writes the final result receipt in a separate transaction after all steps succeed. A failed guard rolls back approval consumption, task changes and checkpoint together. |
| Handoff | `TaskStageStore::handoff` rechecks evidence and commits the destination workflow/state, cleared assignee, task history/audit, and the run's result, handoff outcome and next-step checkpoint together. Provider evidence is refreshed before this transaction. |
| Per-step and final run state | The initial run insert, parameters update and reset to `running` are separate statements. After a step returns, the engine saves its outcome and offset; after the last step it separately saves `succeeded`. Verified branch registry writes in engine `verify_branch` or `TaskBranchOrigin::save` are separate from the later engine outcome save. A succeeded-run retry replays the stored result and can read or save its retry receipt in its own transaction before automatic final dispatch. |
| Run failure and approval request | `TaskTransitionRunStore::fail` authorizes again and commits the run status/error/message with task history sequence, history row and audit. If it leaves `waiting_approval`, project request creation happens afterward, through `ApprovalRequestDefinitionStore::create`. The request insert, its history/audit and keyed receipt commit together, then the engine saves `approval_request_id` separately. The projectless notification insert is separate from the run-failure transaction. |
| Human grant or decision | `TaskApprovalStore::grant_in` inserts the approval, appends task history/audit and updates runs matching task ID, revision, transition ID, fingerprint and `waiting_approval` to `ready`, setting parameters' approval ID and clearing error/message. The direct grant wrapper includes matching pending approval-request updates and receipt in that transaction. The approval-request decision wrapper instead includes the selected request decision, history and receipt. Provider approval prechecks roll back the `consume` they probe; state advance commits it. |
| Notifications | `notify` commits the idempotent in-app or email enqueue/requeue before the separate engine step checkpoint. Migration 0088's SMTP-failure trigger updates the run, increments task history sequence and inserts the failure history row in the same transaction as the failing email status update. The trigger does not append an audit row. |
| Publication and take | `TaskReleaseStore::publish` commits production-publication rows, selected task completion with history/audit, and release status/evidence/audit together, separately from the engine step checkpoint. In repository take, the initial take commits separately from the `__take_branches` run insert. Each branch registration, history/audit and run checkpoint commit together in `TaskCodeStart` after provider checks. The response receipt is handled in a separate transaction. |

`TaskHistoryWriter::event` changes the task history sequence, inserts the history row and calls `AuditWriter::append` on the caller's transaction. `ReceiptWriter::read` acquires a transaction advisory lock and verifies the stored fingerprint for the namespace/actor/operation/request identity.

## Concrete dependencies and ownership

**Dependency direction:** The API adapters (via `nexora-platform-store`) and `nexora-release-worker` depend on `nexora-task-workflow` in `nexora-job-store`. The final package must have zero direct or transitive dependencies on any crate sourced from the API repository, including `nexora-platform-store`, and neither the package nor a helper it calls can delegate execution back to the API. The release worker's runtime graph must satisfy the same boundary. The API continues to own schema initialization and migration checksums.

### Concrete authority chain

- Task and project: `pool_task_scope` calls `TaskScopeAuthority::task` to load the actual task, check capability and apply relation rules. `TaskScopeAuthority::require` delegates to `PlatformAuthority::require` and, for scoped work, `PlatformAuthority::project`. The former locks the active actor, live session or key and matching grants, checks key attenuation and help-desk role restrictions, and the latter locks an unarchived project. `AuthenticationStore::load/refresh` are separate from these transaction checks and enforce ready sessions and absolute expiry when loading credentials. For projectless work, `TaskScopeAuthority::require` permits specific human-role fallbacks after a Forbidden result, and `modify` checks creator, assignee, eligible unassigned reservation or coordination role. Transition authorization and advance additionally require the current actor to be the projectless task's assignee with an eligible role.
- Project relation: `TaskScopeAuthority::{relation,modify}` delegate scoped checks to `TaskReadAuthority::require_relation` → `unrestricted` plus `task_read_predicate`. The unrestricted path checks installation/actor management or project-write grants, then eligible coordination role with live `TasksRead` and project coverage via `actor_roles` and `member_role_projects`. The predicate includes creator, assignee, unassigned pending or active work with the relevant `developer_workflows` membership, and qualifying historical assignment changes. `TaskPolicyStore::scoped_task` obtains the project dependency lock when applicable and locks the scoped task row. Treat these checks as distinct from the initial HTTP/MCP credential adapter.
- Repository binding: `TaskTransitionProvider::source` requires a project and calls `PullRequestSource::load`. That function validates Git policy, enforces `RepositoriesRead` and an unarchived project, reads `repository_metadata(r)`, requires a Git source and calls `RepositoryJobSource::lock`. This locks an active connection and owner, checks connection owner, installation management or a `git_connection_projects` delegation, and then locks the still-authorized repository at the expected revision and returns its current source generation. `PullRequestSource` checks configured hostname, provider and remote ID/name, then matches repository revision/remote ID/generation and connection ID/revision/credential revision across provider calls. `TaskTransitionProviderAuthority::lock` independently captures binding and credential revisions plus `DevelopmentPolicyStore::lock`'s repository policy revision for later equality checks. In repository take, `RepositoryAccess::lock` also requires `RepositoriesRead` and `KnowledgeRead`.
- Remote identity: GitHub uses `GithubRepositoryProof::check` (not `verify`) → `GithubTokenStore::tokens`, `GithubSettingsStore::load` and `GithubClient::{user,installation,repository_token,repository}`. The proof checks the account ID, installation, repository-scoped token and stable repository ID/name against the user and scoped-token views. The transition then uses the connection access token for provider work. GitLab uses `GitlabTokenStore::tokens` and `GitlabClient::{user,repository}` to match account and registered repository ID. Both paths reload `PullRequestSource` and compare it after proof.
