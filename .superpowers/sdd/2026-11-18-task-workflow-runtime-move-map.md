Store modules are in `crates/nexora-platform-store/src`; handlers and MCP dispatch are in `crates/nexora-api/src`. ### Approval paths

- Pool and project POST `/tasks/{task_id}/approvals` → `TaskPoolHandlers::approval_grant` / `WorkItemHandlers::approval_grant` → `grant_pool_task_approval(&mut self, ctx: &AuthContext, id: &str, input: &TaskApprovalGrant)` / `grant_task_approval(&mut self, ctx: &AuthContext, project: &str, id: &str, input: &TaskApprovalGrant)`, both `Result<TaskApproval, PlatformError>` → `TaskApprovalStore::grant` → `grant_in`.
- Project POST `/approval-requests/{approval_request_id}/decisions` → `ApprovalRequestHandlers::decide` → `PlatformStore::decide_approval_request(&mut self, ctx: &AuthContext, project: &str, id: &str, input: &ApprovalRequestDecide) -> Result<ApprovalRequest, PlatformError>` → `ApprovalRequestDecisionStore::decide` → `TaskApprovalStore::grant_in` for approved task targets, in the decision transaction. Denial and document targets do not ready a task transition.
- `grant_in` checks human session, current task and graph, independence, parameters and expiry. It inserts the grant and enriches exact matching `waiting_approval` runs with the approval ID, clearing error/message and setting `ready`. It does not itself execute the transition. Lookup and revocation stay on pool/project HTTP approval routes via `TaskApprovalQueryStore` and `TaskApprovalRevocationStore`. Their signatures are `get_pool_task_approval(&mut self, ctx: &AuthContext, task: &str, id: &str)` and `revoke_pool_task_approval(&mut self, ctx: &AuthContext, task: &str, id: &str, input: &TaskApprovalRevoke)`; `get_task_approval` and `revoke_task_approval` add `project: &str` before `task`. All return `Result<TaskApproval, PlatformError>`. MCP `nexora_task_approval_get` reads and does not grant. `verify_approval` validates via `consume` in a rolled-back transaction before provider writes. `advance` consumes in the same transaction as the state mutation.
- Engine `request_approval` creates the project request through `ApprovalRequestDefinitionStore::create` and nested `PlatformStore::request` with outer request context suspended. `ApprovalOperationPolicy` calls the same transition evaluation to validate a task target. Projectless requests use the in-app notification path in the engine. Direct grant also updates matching pending approval requests and history.

## Runtime behavior that must survive the move

1. Continuation selects oldest `ready` or `waiting_external` older than 30 seconds, ordered by `updated_at,id`, with no claim lock on that select. Load the original credential by ID/method via `AuthenticationStore::load`, validate current actor and grants, and compare actor ID to the persisted row. Sessions must be ready, human, active, unrevoked, and within idle and absolute expiration. API keys must be active, unrevoked, within optional expiry and carry valid scope. Resume does not touch session activity. Conditional updates fail still-eligible rows on credential mismatch or live Unauthorized/Forbidden/NotFound. A storage error from retry propagates. Credential-load errors enter the fallback credential failure branch in the existing code. Other retry errors return `true` after engine handling where applicable. Record these behaviors as baseline, including the possibility of repeated selection or a race between multiple workers, and do not describe this as an atomic claim or guaranteed recovery of `running` rows.
2. `TaskTransitionEngine::execute` reauthorizes and serializes by session advisory lock `task-transition:{id}`. It also locks the receipt identity when present, releases locks and clears scratch facts/checkpoint on normal result paths. Provider HTTP and Git operate outside the state transaction. Durable run identity is task + expected revision + transition + actor + normalized approval fingerprint. `TaskTransitionRunStore` writes each checkpoint, failure or external wait. Replays consult receipts, stored outcomes, provider intents, and checkpoints before repeating side effects. `TaskTransitionRunStore::fail` rechecks task scope and emits task history in its transaction. Keep status and error mapping (`waiting_approval`, `waiting_external`, `failed`) and the exact sent/confirmed intent logic.
3. Load the pinned workflow version, validate graph and current task, then authorize through each step. Supported step paths include approval, push/branch and PR verification, create/merge PR, CI pipeline/deployment verification, contributor rating, code review, state advance, handoff, release publication and notification. Where advance consumes evidence, recheck previously observed provider authorities and live task guards under database locks. Persist `advanced`, `result` and `next_step` with the state change. Handoff preserves task identity and records completion/delivery evidence. The post-advance path can rebuild provider evidence before handoff, so it cannot be omitted as an apparent replay optimization.
4. `dispatch_final` can execute the automatic edge after an eligible governed stage reaches Fin. It handles revision drift, excludes decomposition and same-stage corrective work, clears inherited approval and resolution fields for the new edge, and suspends outer request context. A failing automatic action leaves the completed stage result and its durable run. Terminal self-edge runs do not increment the task revision again.
5. Notifications write durable queue rows with event identities derived from run and step and can requeue failed delivery. Preserve migration 0088's failure trigger and the distinction between a failed notification and a failed task advance. Mail delivery itself belongs to notification processing.

The method-level cuts above require keeping provider/AI credential helpers, not carrying along platform initialization or the general code database runtime. `request` also performs `fresh`, validates the idempotency key and payload bounds, uses installation-key HMAC, and restores context after panic.
